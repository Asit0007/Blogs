I taught myself the job I wanted before it had a posting

I'm a cloud and infrastructure engineer. For about four years I've worked at the unglamorous end of the field — the end where you learn what things actually do when they break.

Incident triage. Root-cause analysis on memory dumps. Disaster-recovery drills. Patch cycles. Keeping enterprise systems alive across hybrid cloud and on-prem estates. It's not the work that gets written about, and it teaches you something the write-ups skip: how systems behave under load, at 3 a.m., when the thing they depend on is down.

Nights and weekends

The work I wanted — cloud-native, infrastructure-as-code, systems I designed end to end — didn't have a posting with my name on it. So I built it myself, after hours. Terraform across three clouds, Go, Python, Docker, CI/CD pipelines, on projects nobody asked me for.

Every one of them got a hard rule it wasn't allowed to break:

  • CloudPulseMust never cost a cent to run. That one constraint dictated every API-design decision.
  • QuantBotRuns unattended on an always-free ARM box with zero open inbound ports — and its dashboard is still public over HTTPS.
  • JobPipeNothing in it logs into a job board. Losing an account mid-search is the worst outcome available, so the tool works one layer down.

The constraint is where the engineering lives. Anyone can build it with an unlimited budget.

The number that was wrong

I built a trading bot and validated it for months against a backtest that reported +90.7% a year. The real figure was +13.7%. Two bugs had been cancelling each other out, inside the one invariant I'd thought to check — every trade reconciled, so nothing looked wrong.

I now trust no number I haven't reproduced myself, from raw inputs, in a second implementation. It's the same discipline you need for evals: an invariant that holds is not proof a system is right.

Now: AI, run properly

I'm pointing the same operator's discipline at AI systems. The part everyone skips — running the thing in production, knowing what it costs per day, knowing why it's slow, knowing what it does when the model API times out — is the part I care about, and the part almost nobody writes about from experience.

So I'm writing it. Build logs, systems explained from the chair of someone who runs things, and a filter on the field — does this actually change what I'd build on Monday? The content I needed didn't exist. The wiring is always hidden. I'm showing it.
