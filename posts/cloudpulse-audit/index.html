A Trap With a 30-Day Delay

AWS Free Tier is a trap with a 30-day delay. You blow past a limit on the 4th and you find out about it on the 1st of next month, in an email, in a currency you didn't budget for. AWS's own Free Tier console is buried several clicks deep, updates on its own schedule, and gives you no at-a-glance signal that anything is wrong.

So I built one. CloudPulse is a single Go binary that pulls the two numbers that actually matter for a one-instance footprint — EC2 instance-hours against the 750/month cap, and data transfer out against 100 GB — plus live CloudWatch metrics, onto one page I could leave open in a tab.

The dashboard was the excuse. The pipeline was the deliverable: code → container → IaC → CI/CD → runtime secrets → a running system, on infrastructure that cost $0/month. And that part worked. For about a year.

Then, in August 2026, I tore the infrastructure down to guarantee the $0. And in September I sat down and read the whole thing back — the Go, the Terraform, the workflow, the git history, and the live AWS account, all open at once.

This post is what that audit found. Short version: three things in this project were confidently, load-bearingly untrue. And not one of them would have been caught by a code review, because not one of them was a bug.

What I Actually Built

One Go binary, no router, no framework, no database. It serves three JSON endpoints and a static HTML frontend from the same process on the same port, and it ran as one Docker container on one t3.micro, next to a second container running Vault. 

Internet
  │  :80
  ▼
EC2 t3.micro (default VPC, public subnet, IAM instance profile)
  ├── docker: cloudpulse-app  -p 80:8080
  │      ├──→ AWS CloudWatch API  (creds via instance profile)
  │      └──→ api.github.com      (PAT read from Vault at boot)
  └── docker: vault-server    :8201  (file storage, KV v2, tls_disable)

The boot sequence is strict and fail-fast, with exactly one deliberate exception:

go// main() — backend/main.go:418
initVault()    // FATAL on failure — no Vault, no app
initAWS()      // returns nil EVEN ON FAILURE  ← deliberate, see below
initGitHub()   // FATAL on failure — reads the PAT from kv/cloudpulse

http.Handle("/", http.FileServer(http.Dir("./frontend")))
http.HandleFunc("/api/ec2-usage",       ec2UsageHandler)
http.HandleFunc("/api/github-users",    githubUsersHandler)
http.HandleFunc("/api/free-tier-usage", freeTierUsageHandler)

http.ListenAndServe(":" + PORT)

Every decision in there has a reason, and two of them come back to bite later in this post:

DecisionRationale
No router, no framework, no DB Raw net/http keeps the binary small and the dependency surface auditable — six direct dependencies total. A database would have meant RDS (not free forever) or self-managed storage. The app is stateless by design and that's the one architectural choice I'd defend without qualification.
Vault for the GitHub PAT Not an environment variable. The token is fetched at boot from KV v2 at kv/cloudpulse using a policy-scoped token, never root. This is the whole point of the project's security story — hold that thought.
Metrics derived from CloudWatch, never Cost Explorer Cost Explorer bills $0.01 per API call. On a project whose entire premise is $0/month, paying AWS to tell me how much I'm paying AWS was the one thing I couldn't do. So the free-tier numbers get derived from free metrics instead. This is Lie #2 in embryo.
Terraform validation blocks The instance type variable accepts t2.micro or t3.micro and nothing else; the EBS size accepts 8–30 GB. Not a warning — a plan that refuses to generate. This turns out to be the most valuable thing in the repo.
initAWS returns nil on failure The one exception to fail-fast. If the EC2 metadata call fails, the app still starts — because off-EC2 that call should fail, and local development shouldn't require an EC2 instance. Separating "cannot start" from "starts degraded" is a real distinction and I got it right here.

Lie #1 — The Docs Described a System That Never Existed

For roughly a year, three documents in this repo — the README, docs/ARCHITECTURE.md, and my own workspace notes — described a deployment on AWS ECS Fargate, with images in ECR, and a Prometheus /metrics endpoint on the Go binary.

None of it had ever existed.

What the docs said
  • Deployed on ECS Fargate
  • Images pushed to ECR
  • /metrics endpoint scraped by Prometheus
  • Requires Go 1.21+
  • IAM policy follows least privilege
What the code did
  • main.tf has zero ECS resources — one aws_instance, one SG, an IAM trio
  • deploy.yml logs into Docker Hub and SSHes to a box
  • main.go registers exactly three routes; go.mod has no client_golang
  • go.mod declares go 1.25.0
  • Eleven actions on Resource = "*", including write. The code calls two.

The question worth asking isn't how did this happen — it's why did it survive a year. And the answer is uncomfortable: documentation doesn't drift. It gets written once, in the optimistic mood of the design phase, when Fargate was still the plan and Prometheus was still next weekend's job. Then the code walks away from it, and nothing ever forces the two to argue out loud.

"There is no compiler for prose. The README is the only artifact in the repo that can be wrong for a year without anything failing."

The tell was a file called monitoring/prometheus.yml. It's real. It's syntactically valid. It has four scrape targets. And every one of them points at a /metrics endpoint that has not existed for a single second of this project's life. It isn't a lie so much as a fossil of an intention — a config file for a system I fully believed I was about to build, sitting there for a year as evidence that I hadn't.

Fixing this is a fork in the road: (a) make the docs true, or (b) make the code true. Option (b) is a week — ECR repo, ECS cluster, task definition, service, ALB, target group, execution role, plus the /healthz endpoint I also didn't have. Option (a) was an afternoon.

I took (a), and I'd argue that's the right call far more often than engineers like to admit. A README that accurately describes a single EC2 box is worth strictly more than one claiming a Fargate service you can't produce on request. The first is a system. The second is a story about somebody else's system, and the moment anyone technical looks closely, it stops being a portfolio piece and starts being a credibility problem.

Lie #2 — The Dashboard Measured the Calendar

This is the one that stings, because it isn't a doc or a config file. It's the feature. Here is how the dashboard calculated your EC2 free-tier hours: 

go// backend/main.go:308 — freeTierUsageHandler
now          := time.Now().UTC()
startOfMonth := time.Date(now.Year(), now.Month(), 1, 0, 0, 0, 0, time.UTC)

ec2HoursUsed := now.Sub(startOfMonth).Hours()   // ← this is not instance runtime

That is not instance runtime. That is the calendar. It measures how far into the month it currently is. It happens to equal your instance-hours if — and only if — you are running exactly one instance and it has been up continuously since the 1st.

Stop the box for a week to save hours, and the number the dashboard shows you does not move. Run two instances, and it under-reports by half. It is a clock wearing a lanyard that says metrics.

In fairness to past-me: the code says so. There's an honest comment sitting directly above that block. But the comment is in main.go and the number is on a webpage, in 32px type, next to the words "hours used" — and nobody reads the source of a dashboard they built specifically so they wouldn't have to think about the thing it displays.

The egress number is wrong more subtly, and in two directions at once. It sums NetworkOut for this one instance, while the real 100 GB allowance is account-wide across every service. And NetworkOut counts traffic AWS may never bill as internet egress at all — intra-VPC, intra-AZ. It over-counts one way, under-counts the other, and the two errors do not have the courtesy to cancel.

But the worst one is the silent one

ec2UsageHandler checks whether it actually knows its own instance ID, and returns 503 if it doesn't. freeTierUsageHandler — the very next function in the same file, written the same afternoon — does not.

So: run it off-EC2 with no EC2_INSTANCE_ID_OVERRIDE set. The handler calls CloudWatch with an empty InstanceId dimension. CloudWatch doesn't error on that — it returns an empty set of datapoints, which is a perfectly reasonable answer to a nonsense question. The sum of nothing is zero. And the dashboard renders: 

json{
  "ec2HoursUsed":             456,
  "dataTransferOutUsed":      "0.00",
  "dataTransferOutRemaining": "100.00"
}

Maximum headroom. Nothing to worry about. Delivered with total confidence by a process that does not know which computer it is running on.

That is the worst failure mode in the entire codebase, and it is not a crash — it is the absence of one. A 503 is honest. 0.00 GB used / 100.00 GB remaining is a lie that looks exactly like good news, rendered on the one panel whose whole job is to tell you bad news early.

"A crash is honest. A confident zero, in green, from a process that doesn't know which instance it's on — that's the expensive kind of wrong."

What makes this genuinely interesting is that the rest of the file gets it right. When a CloudWatch metric has no datapoints, ec2UsageHandler returns the string "N/A" in a numeric JSON field, and the frontend explicitly checks for that sentinel before it will parseFloat anything. That's a deliberate, slightly ugly, completely correct decision: refuse to render a zero you didn't measure. I made that call in one handler and forgot it in the one directly below.

A constant with an expiry date nobody wrote down

The 750.0 hour and 100.0 GB caps are hardcoded float literals. In July 2025, AWS moved new accounts to a credits-based free plan instead of the perpetual 750-hours model. Those two numbers are now correct only for legacy accounts. Point this dashboard at an account opened after that date and the entire free-tier card becomes decorative — and nothing in the code knows.

Lie #3 — The Security Story

The README has a capabilities table. One row of it reads:

"Security — IAM roles, runtime secret fetch from Vault, .gitignore hardening"

Every clause in that sentence is true. The row is still a lie, because of what it leaves out.

While the application was dutifully fetching its GitHub PAT from Vault at boot — never from an env var, exactly as designed — there was a file sitting in the project directory called SetUpVaultSecrets.sh. It's a scratchpad: everything I learned while wiring Vault up, saved so I'd never have to re-learn it. Genuinely useful. It also contained, in plaintext:

  • a GitHub Personal Access Token, pasted six times
  • an AWS access key ID and its secret access key, three times
  • five Vault unseal keys and two initial root tokens
  • a long-lived application token
  • the AWS account ID, live instance IDs, and public IPs

The good news, and I did check: git log -- SetUpVaultSecrets.sh returns nothing at all. That file has never been committed, not once — and neither has the tfstate or the tfvars. The .gitignore hardening in that README row did precisely what it claims.

The bad news is that .gitignore is not a security control. It's a filter on one exfiltration path. It does nothing whatsoever about the file existing, in cleartext, on a laptop, for fifteen months — which is exactly how long the AWS access key inside it remained Active. I verified that against the live account during this audit, six months after I'd first flagged it to myself in my own notes.

And here's the part I'd want anyone to take away from this section: the August 2026 teardown deleted the compute and left both the file and the IAM identity completely untouched. Destroying the instance felt like closing the issue. It closed nothing. Tearing down infrastructure is not credential rotation, and the feeling that you've cleaned something up is not the same as having cleaned it up.

".gitignore kept the secret out of the repository. It has never once kept a secret out of a file."

Even the part I designed properly undercut itself

Set the scratchpad aside entirely. The deployment I actually intended still had four holes in it:

01
VAULT_TOKEN as a container env var
Anyone with shell access to the box could read it straight out of docker inspect cloudpulse-app, /proc/<pid>/environ, or docker exec … env. The entire point of Vault was not keeping secrets in environment variables — and the key to the vault was in an environment variable.
02
Vault ran with tls_disable = true
The token and the secret crossed the Docker bridge in cleartext on every boot. The config file itself carries the warning, in capitals: NOT FOR PRODUCTION INTERNET FACING. I wrote that line and then deployed it to something internet-facing.
03
Zero authentication, and CORS wide open
Every endpoint was unauthenticated and set Access-Control-Allow-Origin: *. Anyone who could reach port 80 learned my instance ID, my utilization, my egress volume, and my full repo collaborator list with roles. Instance IDs are useful reconnaissance. And any website could read all of it out of a visitor's browser.
04
An IAM policy that wasn't least privilege
Eleven actions on Resource = "*" — including cloudwatch:PutMetricData and five logs: write actions. The application only ever reads metrics; it calls two of the eleven. The README claimed least privilege. The policy had never earned it.

I had built the shape of secrets management — and it's a real shape: init, unseal, KV v2, a policy-scoped token instead of root. Learning that lifecycle properly was the most valuable part of the whole project. What I hadn't built was the discipline around it. The runbook that taught me how to do it right was itself the thing leaking.

The fix that would actually earn that README row is the Vault AWS auth method: the application authenticates using its own IAM instance profile and receives a short-lived token in return. No static token in the deployment, in CI, or anywhere else — which means there is nothing to paste into a scratchpad in the first place. It's a day of work, and it is the single most valuable change still available in this repository.

What Was Actually Right

Having spent two thousand words prosecuting myself, the defense — because several things in here hold up, and one of them turned out to matter more than the entire dashboard:

  • The "N/A" sentinel. A missing metric renders as "N/A", never as 0. Refusing to display a number you didn't measure is the correct instinct, and the frontend was written to respect it.
  • A 2-second timeout on the instance metadata call. Without it, running off-AWS hangs on a link-local address until TCP gives up — which on some stacks is two full minutes of a developer wondering what they broke.
  • initAWS returning nil on failure. The one deliberate exception to fail-fast, documented in-line so future-me wouldn't "fix" it. "Cannot start" and "starts degraded" are different states and deserve different handling.
  • Independent per-card failure in the frontend. Three parallel fetches, three independent try/catch blocks. One dead endpoint degrades one card instead of blanking the page.
  • Honest comments at the point of approximation. Every derived number has a comment above it explaining what it actually measures. That's the only reason this audit was possible at all.

And then there's the one that reframed the whole project for me:

hcl# terraform/variables.tf
variable "ec2_instance_type" {
  validation {
    condition     = contains(["t2.micro", "t3.micro"], var.ec2_instance_type)
    error_message = "Instance type must be free-tier eligible."
  }
}

Not a comment. Not a note in the README. Not a dashboard card you have to remember to look at. A terraform plan that refuses to run. There is no sequence of tired 11pm keystrokes that gets a t3.large into that account, because the tooling will not produce a plan containing one. The EBS volume size has the same guard: 8–30 GB or nothing.

Which leads to the conclusion I genuinely did not expect to reach when I opened this repo:

"The 456-line dashboard I built to watch my AWS bill never saved me a cent. The eight lines of Terraform that refused to plan an expensive instance did."

Detection is a story you tell yourself about the future — it only works if the alert fires, and you see it, and you act. Prevention happens whether or not you're paying attention. I built an elaborate, containerized, Vault-backed, CI/CD-deployed detection system, and shipped its only real safety feature as a footnote in a variables file.

Teardown, and What's Still Standing

May 2025
Built and deployed. Terraform apply, Vault initialized by hand over SSH, GitHub Actions pushing to Docker Hub on every merge to main.
May 2025 → Aug 2026
Running, and quietly diverging from its own documentation. Nothing failed, so nothing prompted a re-read.
19 Aug 2026
Infrastructure decommissioned to hold the account at $0. The deploy workflow was switched to manual dispatch so it would stop SSHing to a host that no longer existed.
2 Sep 2026
Full audit against the code, the git history, and the live AWS account. Docs reconciled with reality. This post.

Two things outlived the teardown, and both are instructive:

Three IAM resources survived the destroy — the role, the policy, and the instance profile. They cost nothing and they're invisible in the console unless you go looking. They are also precisely enough to make the next terraform apply fail with EntityAlreadyExists instead of cleanly rebuilding the stack. A teardown that leaves debris shaped exactly like a future collision.

The local state file is confidently obsolete. terraform.tfstate, serial 13, dated May 2025, still lists all six managed resources as present and one EC2 instance as running, at a public IP that hasn't answered in over a year. The destroy was run from a different working directory, so this copy of state never heard about it. Local state, no S3 backend, no lock table, single operator.

State is not truth. State is a recording of the last thing Terraform was told — and I told it from somewhere else.

Two operational lessons worth stealing

The secrets manager was the availability single point of failure

Vault in file-storage mode seals itself on every restart. Dev mode auto-unseals; production mode categorically does not. So the chain was: instance reboots → Vault comes back sealed → the app FATALs at boot because it can't read the PAT → Docker's restart: unless-stopped puts it into a crash loop → the dashboard stays down until a human SSHes in and types an unseal key from memory. This was the number one cause of downtime, by a wide margin. The component protecting the secret became the thing most likely to take the service down.

No Elastic IP, and a whole class of recurring breakage

The instance had a dynamic public address, so it changed on every stop/start — silently invalidating the EC2_HOST_IP deploy secret, the Prometheus scrape target, and every bookmark. That Prometheus config still points at an address that is two instances stale. An Elastic IP is free while attached to a running instance. Skipping it saved nothing and cost an afternoon, repeatedly.

The Fix List

Ordered by value per hour of effort, which is not the same as ordered by how interesting they are:

  1. Rotate the credentials in the scratchpad and strip the values out, keeping only the commands. The runbook value is real; the pasted secrets are pure liability. Non-negotiable, and the reason this post exists instead of a screenshot of a dashboard.
  2. Give the server explicit timeouts. A bare ListenAndServe has no ReadTimeout, WriteTimeout, or IdleTimeout — textbook Slowloris exposure on a public port. Five lines, and the highest value-per-line hardening available anywhere in the repo.
  3. Add GET /healthz. A prerequisite for a load balancer, for ECS, for any real monitoring — and I'd spent a year documenting a Fargate deployment that would have required one.
  4. Allocate an Elastic IP. Free while attached. Kills an entire recurring failure class.
  5. Guard instanceID in the free-tier handler so it returns an error instead of a confident zero.
  6. Change ssh_access_cidr's default from 0.0.0.0/0 to something that fails safe. There is no good reason for the permissive value to be the default, and the variable's own comment admits it.

Then the work that's actually worth putting on a résumé: Vault AWS auth to remove the last static token; real Prometheus instrumentation so prometheus.yml stops being fiction; Terraform state in S3 with DynamoDB locking; image tags carrying the commit SHA so a rollback is docker run <sha> instead of a revert-and-redeploy; and tests, which need the three package-level global clients extracted behind interfaces first.

The Common Thread

Three lies, one theme: none of them were bugs. Every one of them ran, returned 200, and looked correct. The docs compiled fine, because prose always does. The dashboard rendered a number in the right font with the right units, and it was the wrong number. The security row in the README was true clause by clause and false as a claim.

Code review catches code. It does not catch a README describing a different system, a metric that measures the calendar, or a text file two directories away with your access key in it. The only thing that catches those is sitting down, fifteen months later, and reading your own work as though a stranger wrote it and you are not especially inclined to believe them.

Do that with the AWS console open in the next tab. Mine had something Active in it.
