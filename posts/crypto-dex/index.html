The SDK That Vanished

Crypto-DEX is a multi-chain DEX aggregator and wallet dashboard that runs with no backend at all — every read delegated to a hosted Web3 API, every swap route to a plugin running on someone else's server. Then the vendor discontinued that product. This is the log of moving the entire data layer onto wagmi and viem without adding the backend the project existed to avoid — the reframing that turned a 19-file rewrite into 3, and the security finding that finished the last 3 in a hurry.

01The Bet: Someone Else's Infrastructure

Building an Ethereum dApp that shows a user their own portfolio is deceptively expensive. "Which ERC-20 tokens does this wallet hold?" is not a question the blockchain answers. There is no getMyTokens(). To answer it yourself you run an archive node, a log-scanning service that watches every Transfer event ever emitted, a token-metadata cache, and a price oracle. That is four pieces of infrastructure before you have rendered a single row.

Crypto-DEX sidestepped all of it. Every read went to Moralis' hosted Web3 API; every swap route went to the 1inch aggregator plugin, which ran server-side inside a Moralis Server instance. The result was a genuinely useful multi-chain DEX and portfolio viewer that deployed as a static bundle. No servers, no database, no ops.

That is a good trade. Renting someone's indexing infrastructure is cheaper than running your own, and for a side project it is not close. The bet you are making — usually without writing it down — is that the vendor stays in the business you are depending on them for.

"No servers to operate" is not the absence of a dependency. It is a dependency you have moved somewhere you cannot see it.

02The SDK Vanished

Moralis discontinued managed Moralis Servers and moved to an API-key-only model. The app was pinned to moralis@1.2.4 / react-moralis@1.2.1 — the generation built entirely around the appId + serverUrl pair. Those two strings now resolve to nothing. Not a deprecation warning you migrate at leisure: the product the SDK talks to no longer exists.

What that took with it, in ascending order of how annoying it was to discover:

Everything that stopped working at once
  • The app could not boot. src/index.js threw unconditionally when the two env vars were missing. Not "degraded" — a white screen.
  • The DEX page was dead. Moralis.Plugins.oneInch was a server-side plugin, installed per Moralis Server. No server, no plugin.
  • The on-ramp was dead for the same reason (Moralis.Plugins.fiat).
  • The live event feed was dead — useMoralisQuery("Events", …, { live: true }) needs the server's WebSocket and database.
  • Every read hook was dead — balances, transfers, NFTs, prices, domain resolution.

The second item is the one worth sitting with, because of how it failed. useInchDex guards its entry point like this: 

if (!Moralis?.["Plugins"]?.["oneInch"]) return null;

That is a defensive guard written by someone sensible. It is also, once the plugin is gone forever, a permanent silent failure. The token picker simply never populates. No exception, no console error, no failed network request to notice in devtools. The UI renders perfectly and does nothing. A user's only signal is an empty dropdown.

A vendor outage pages you. return null does not.

And it was not one vendor. @walletconnect/web3-provider@1.7.1 is WalletConnect v1, whose bridge servers were shut down in the same era. The WalletConnect tile in the connect modal hung. Two independent vendors, the same story, the same year — which stops looking like bad luck and starts looking like the base rate for hosted Web3 infrastructure.

The honest assessment at this point was: budget this as a rewrite of every hook in src/hooks/, not a dependency bump. The React presentation layer is salvageable. The data layer is not.

03Fixing Everything That Wasn't the Problem

The first phase of work touched the data layer almost not at all. That looks like procrastination and was the opposite.

A data-layer migration destroys and rebuilds every hook in the project. The thing that survives it is the presentation layer — the components, the routing, the build. If those are a mess, you carry the mess across the migration and then cannot tell which of your new bugs are new. So the floor gets swept before it gets ripped up.

Build toolchain: CRA → Vite 5. react-scripts gone, entry moved to src/main.jsx, output to dist/. Node 22+ as a floor rather than an exact pin, so a local Node 25 doesn't trip EBADENGINE. Tailwind 3 added with preflight off, because antd v4's dark theme owns the reset and two resets fight.

Deleted outright: the service worker, src/context.js, src/uikit/, src/style.css, the WalletConnect v1 connector, and magic-sdk. Along with something more interesting — five duplicate wallet tiles.

Six of seven connectors did the same thing

Trust, MathWallet, TokenPocket, SafePal and Coin98 were visually distinct tiles in the connect modal that all carried connectorId: "injected". Every one of them connected to window.ethereum and nothing else. Clicking "Trust Wallet" on a desktop with only MetaMask installed connected MetaMask, with no warning and no indication anything unexpected had happened. Five tiles promising five things and delivering whichever wallet you already had.

Two security fixes landed here too, and both were the kind that only show up when you read code you did not write. 1inch approvals were unbounded — the classic infinite-allowance pattern — and are now bounded to the swap amount. Slippage was hardcoded and is now user-configurable in the DEX UI, defaulting to 1%. Every alert() became an antd notification, and a hotlinked third-party image in the header went away.

None of that fixed the dead SDK. All of it meant that when the SDK migration started, every failure was attributable.

04The Plan Was Written by a Machine, and It Was Wrong Twice

This project carries a claude.md — a long working document generated by reading the codebase end to end: source, contracts, build tooling, git history, config. It holds the architecture map, the known bugs, the security notes, and the thing that mattered most here: a worked-out migration plan with a numbered execution order, a per-hook migration map, a list of anticipated traps, and a set of open decisions to settle before step one.

I want to be precise about what was and wasn't valuable, because "AI wrote my migration plan" is the kind of claim that usually evaporates on contact with detail.

The plan was wrong twice.

PredictedReality
wagmi would resolve to v2. It resolved to v3. Same API surface, no plan changes.
Trap #1: wagmi v2 needs React 18, but react-moralis pins React 17 — so the migration must be a big-bang cutover. react-moralis peers react >=17. It does not pin. The entire premise of the most feared trap was false, and the incremental path was available all along.

Trap #1 being wrong is the single most consequential fact in this whole migration. If it had been right, there would have been no way to move one component at a time — the app would have had to leave Moralis in one commit, with every hook rewritten simultaneously and no working state in between. Instead, the two SDKs could sit side by side for weeks.

So the plan's predictive accuracy was mixed. Its actual value was structural: it was specific enough to be proved wrong in a named place. "Trap #1 does not apply" is a sentence you can only write if someone wrote down trap #1 first. A vague plan cannot be falsified, so it cannot teach you anything when reality diverges.

Addenda that supersede rather than overwrite

The convention that made the document survive its own obsolescence: every phase appends a dated addendum that states explicitly what it supersedes — "supersedes §4.7, §7.2, the Phase-1 addendum's React 17 line, and the 'not started' status on the Phase 2 Plan." The stale sections stay, annotated, rather than being quietly edited away. Six months later you can read what was believed at the time and what replaced it, which is the difference between a document and a changelog.

A plan's job is not to be right. It is to be wrong somewhere specific enough that you learn something when it breaks.

05Coexistence, Not Cutover

With trap #1 dead, the strategy became: mount both SDKs at once and migrate component by component, keeping the app shippable at every commit.

The provider stack is WagmiProvider → QueryClientProvider → MoralisProvider. The last one is the trick: 

<MoralisProvider initializeOnMount={false}>

The Moralis context stays alive so the not-yet-migrated hooks still compile and mount, but nothing ever tries to connect to the server that no longer exists. The app renders normally instead of being pinned to a "configure your credentials" screen. Dead hooks return empty; live components work. That single prop is what bought the incremental path.

The wallet layer went first — Account, Chains, RequireWallet, Address, Blockie, App — moving to useAccount, useConnect, useDisconnect and useSwitchChain. Two things got deleted rather than ported: the enableWeb3 reconnect useEffect in App.jsx, and the localStorage.connectorId key. wagmi persists and reconnects on its own, so hand-rolled session restoration is now just a bug surface.

The wallet cutover is also what finally killed those five duplicate tiles for good. wagmi owns the connector list, so tiles now reflect the wallet actually installed. Account/config.js shrank to icon resolution and nothing else.

One source of truth, converted at the boundary

src/helpers/wagmi.js derives its transports from the existing helpers/networks.js, falling back to viem's public RPC. networks.js stays the single source of truth; wagmi reads from it, not the other way round. The chain-id representation problem — wagmi speaks decimal, networkConfigs is hex-keyed — is solved by toHexChainId() and getNetworkConfig(): normalize on decimal internally, convert only at the boundary. Nearly every chain-id bug in this codebase came from doing that conversion ad hoc in ten places.

06The Real Question Was Never "Reads vs Writes"

The plan sequenced the work as reads first, then writes, and gated the whole sequence on getting an Alchemy API key. Step 5 could not begin, the reasoning went, until that key existed.

That was wrong, and noticing why is what collapsed the remaining work.

"Reads vs writes" is the wrong axis entirely. The axis that actually matters is does this question require an indexer?

CategoryWhat it coversNeeds a key?
Answerable by RPC Anything a plain eth_call, eth_getBalance or eth_getLogs can serve: native balance, ENS resolution, contract reads, contract writes, live event watching. No
Needs an indexer Anything requiring enumeration over an address's history: which ERC-20s does this wallet hold, list its transfers, list its NFTs. Yes

Contract writes need no key. Live event watching needs no key. ENS needs no key. All three had been mentally filed under "later, after the credentials land" purely because they were downstream in a numbered list.

wagmi's configured transports already provided the entire first bucket. Everything in it shipped in one pass, with no credentials at all — and the count of files still touching Moralis dropped from 19 to 3 in that single pass.

The question is not whether it reads or writes. It is whether any RPC method can answer it at all.

Concretely, that pass delivered: NativeBalance on wagmi's useBalance(); Transfer on useSendTransaction for native and useWriteContract + viem's erc20Abi for tokens, with useWaitForTransactionReceipt driving the receipt notification and an isAddress() guard before sending; AddressInput on useEnsAddress pinned to mainnet.id, because ENS lives on mainnet regardless of which chain the wallet is pointed at.

The Contract console went to viem end to end, and picked up three fixes on the way. pure is now treated as a read alongside view — it had been mislabelled as a transaction, meaning the UI offered to spend gas on a function that cannot change state. A new coerceArg() maps antd's always-string form fields onto real ABI types. And results now serialise through a BigInt-aware replacer, because plain JSON.stringify throws outright on the BigInts viem returns. That last one also fixed falsy results: 0, false and "" had been hidden by a truthiness check, so a function correctly returning zero looked broken.

Live events were the pleasant surprise. useWatchContractEvent replaced the Moralis live query and polls over the existing HTTP transport — no WebSocket RPC, no key. The tradeoff is that there is no history, only events arriving from now on. The card says so in the UI rather than pretending otherwise, and caps at 20.

07Three of Six RPC Endpoints Were Dead

Found while verifying the above, and this is the one that would have quietly ruined everything: since wagmi's transports are derived from networks.js, a dead endpoint there breaks every read migrated in the previous section — with no error attributable to the migration itself.

ChainOld endpointStatusReplaced with
Ethereum 0x1eth.llamarpc.comHTTP 521ethereum-rpc.publicnode.com
Polygon 0x89polygon-rpc.comHTTP 401polygon-bor-rpc.publicnode.com
Sepolia 0xaa36a7rpc.sepolia.orgHTTP 404ethereum-sepolia-rpc.publicnode.com
BSC / BSC-testnet / Avalanche—AnsweringLeft alone

Three different failure codes for the same underlying condition, none of which is a network error your code can catch and interpret. rpc.ankr.com/eth, the obvious reflex replacement, is now key-gated and answers -32000 Unauthorized.

Free public RPCs rot silently, and no test catches it

These endpoints were correct when they were written down. Nothing in the repository — not a lint rule, not a unit test, not the build — has any opinion about whether a URL in a config file still answers. The only thing that catches this is actually calling them, on purpose, periodically. Re-run a health check before trusting the replacements above; they will rot too.

08The Indexed Half

That leaves the bucket that genuinely cannot be served by an RPC. src/helpers/alchemy.js is the new read layer, and it is raw fetch, not alchemy-sdk. This is three JSON-RPC methods and one REST call; the vendor chunk is already around 3.2 MB, and an SDK to wrap four HTTP requests is not a trade worth making.

Hook / componentAlchemy call
useERC20Balancealchemy_getTokenBalances, then alchemy_getTokenMetadata per non-zero holding
useERC20Transfers / useNativeTransactionsboth wrap a new useAssetTransfers — alchemy_getAssetTransfers, with category the only difference between them
useNFTBalances (new)getNFTsForOwner on the nft/v3 REST base

All three are useQuery-backed — react-query is already in the tree for wagmi, so caching came free — keyed on [chainId, address] with a 30–60s staleTime.

Three things about Alchemy that cost time and are worth writing down:

The three that bite
  • Alchemy cannot OR fromAddress with toAddress. "All transfers involving this address" is not one query. useAssetTransfers issues two calls and merges them newest-first.
  • value comes back already decimalised as a JS number, not wei. The old Moralis.Units.FromWei calls in the tables were deleted rather than replaced — a subtle one, because wrapping an already-decimal number in a wei converter produces a plausible-looking tiny number rather than an error. Raw wei is still in rawContract.value if precision matters.
  • chainId is decimal, networks.js is hex-keyed. The tables convert at the call site. getExplorer silently returns undefined on a decimal id — that is exactly how every block-explorer link would have broken, with no error anywhere.

isAlchemySupported(chainId) gates all three. When it returns false the views render a new DataNotice component, which deliberately distinguishes the two reasons it can fail: no key configured versus a chain Alchemy's enhanced APIs don't cover (BNB Chain, localhost). Those are different problems for the user and collapsing them into one "no data" state is how you get bug reports you cannot action.

One deployment consequence: VITE_ALCHEMY_API_KEY ships in the browser bundle. That is a deliberate choice — the alternative is proxying every read through a function and losing edge caching — which makes the domain allowlist on the Alchemy app the entire protection. If that allowlist is not configured, the key is public. It is worth being blunt about that rather than describing the variable as "browser-safe" and moving on.

Some things got deleted instead of migrated, which is usually the best outcome available. useVerifyMetadata and useIPFS are gone: Alchemy returns resolved metadata and a cached HTTP media URL, so the lazy token_uri fetch, the ipfs:// rewrite and the OpenSea throttle-retry all became dead weight. Unstoppable Domains was dropped — no keyless replacement exists. The fiat on-ramp and its Ramper component were cut, because every real provider needs a commercial KYC'd account.

A last detail that is pure trap: Alchemy reports NFT tokenType as "ERC1155", uppercase. The Moralis code it replaced compared against lowercase "erc1155". A string comparison that silently never matches, sending every ERC-1155 down the ERC-721 transfer path.

09What I Haven't Verified

Most migration write-ups end at "it compiles and the build is green." That is a much weaker claim than it sounds, so here is the actual verification state, split three ways.

Confirmed live, through the running app against mainnet: ENS resolution (vitalik.eth → 0xd8dA…6045); readContract against USDC returning symbol → "USDC", totalSupply → 50613753740569914 — which is specifically the BigInt path that JSON.stringify throws on — and balanceOf with an address argument; real USDC Transfer events streaming into the events card; and RPC health across all six endpoints. lint:check, prettier:check and build all clean.

Shape-confirmed only, against Alchemy's public demo key: getNFTsForOwner and alchemy_getAssetTransfers. Every field the mapping code reads was present and had the expected type, but this is not the same as running it with a real key under real quota.

Not confirmed at all

alchemy_getTokenBalances and alchemy_getTokenMetadata — the demo key returned 429 throughout, every attempt, so the ERC-20 balance path has never once executed successfully end to end. The DataNotice render is also unconfirmed, since it needs a connected wallet in a failure state.

Both are low-risk: the request shapes are documented and stable, and DataNotice reuses RequireWallet's exact token classes. Low-risk is not verified. These are the first two things to check when a real key lands, and if something in this migration is broken, the honest prior is that it is one of them.

One more thing sits in this category, and it arrived with the section below. vite-plugin-node-polyfills is still installed, and on the face of it should not be: it exists to satisfy Moralis v1's need for Node built-ins in the browser, and Moralis is gone. It pulls crypto-browserify and therefore elliptic back into the dev tree. Nothing imports node crypto any more, so none of it reaches the bundle — checked, rather than assumed: dist/ has zero hits for crypto-browserify, browserify-sign, create-ecdh or bn.js.

So removing it is probably right and probably safe. It is still installed because some WalletConnect builds reach for Buffer at runtime, and a green build would not catch that — only connecting a real wallet in a real browser would. That is the same class of problem as everything else in this post, so it gets the same treatment: a comment in vite.config.js saying exactly why it is still there and what would have to be checked to take it out, rather than a confident deletion.

10Step 9 Jumped the Queue

The plan's last two steps were step 8, reconnect the swaps, then step 9, delete Moralis. It happened in the other order, and the thing that reordered it was not on any axis the plan had.

Those last three files kept moralis and react-moralis in package.json. Those two drag ethers@5.6.0, and through it elliptic and crypto-js@4.1.1. Run the audit the way that actually matters — npm audit --omit=dev, production tree only — and that is 13 vulnerabilities, 6 of them critical, in the shipped bundle of an app whose entire purpose is asking people to connect a wallet.

The detail that made it non-negotiable rather than a scheduling question: elliptic's vulnerable range is *. There is no published version that is fixed. No pin helps, no overrides entry helps, no amount of waiting for an upstream release helps, because there is no release to wait for. The only fix available is not having the dependency. wagmi and viem sign with @noble/curves and never needed it.

So step 9 was pulled forward and Moralis came out entirely. package.json now contains zero occurrences of the string. Prod audit: 13 vulnerabilities, 6 critical, to 0.

What came out with it, stated rather than papered over

The swap engine. It was Moralis.Plugins.oneInch, and it had been dead for a long time already — the v1 servers are gone, so the plugin had nothing to call. The page was failing at runtime rather than saying so. It now says so: the panel still renders, it shows a notice, the button reads “Swapping unavailable,” and useInchDex.js keeps its exact interface so DEX.jsx needs no restructuring when 1inch is reconnected. Three function bodies to fill in, and a note to delete.

That is the trade worth being explicit about. Deleting the dependency did not break swapping; swapping was already broken. What deleting it changed is that the app stopped pretending otherwise. The feature moved from silently dead to visibly off, which is a real improvement even though the capability is identical — zero either way.

A broken feature and a disabled feature do the same amount for the user. Only one of them tells the truth about it.

The rest of the removal was small replacements, and one of them is a judgement call. useChainId from wagmi took over Moralis' chainId, converting decimal to hex at the boundary as everywhere else. viem's formatUnits replaced Moralis.Units.FromWei. The isServerInfo plumbing came out of main.jsx, App.jsx and QuickStart, because once nothing reads a Moralis server the question “are Moralis credentials configured?” has no meaning. And the USD price rows, which came from Moralis' price oracle, now render null rather than a stale or an invented number — an empty cell is worse-looking and more honest than a plausible figure with nothing behind it.

The one step still open

Reconnecting the swaps is contained, and it was deliberately kept out of a security commit rather than rushed in alongside one:

  • Step 8A key from portal.1inch.dev, behind a serverless function. The v5/v6 API requires auth, unlike the version this was originally written against. The key must not be VITE_-prefixed — that prefix inlines it into the browser bundle, which is exactly how VITE_ALCHEMY_API_KEY works and precisely why that one needs a domain allowlist to be safe at all.
  • Step 8Fill in three functions in useInchDex.js — getQuote, trySwap, and the tokenList fetch — with approve and swap going through wagmi's useSendTransaction instead of the plugin's own signer.
  • Step 8Do not regress the Phase-1 security fixes. Bounded approvals and user-set slippage were fixed once already, back in section 03. Reintroducing an infinite allowance while porting this would be easy and nothing in the repository would fail.
  • CleanupRestore the USD prices from the quote provider. They are wired to render null. A spot price from whoever is already answering the quote is the natural place to get them back, rather than adding a fourth vendor for one column.

Moving hosting to Vercel earlier in the project is what makes that shape available at all. GitHub Pages is static-only, so there would be nowhere to put the key: the choice would have been between shipping a 1inch credential to the browser and cutting swaps permanently. One serverless function is a far smaller concession than the backend this project was built to avoid.

The Migration Is Done and the App Does Less

Both halves of that are true, and the second one is not a failure. The data layer is entirely off the dead SDK, the production bundle is clean, and swapping — which had not worked for a long time before anyone wrote it down — is now switched off in the open instead of failing behind a guard clause. One step is left, deliberately, because it needs a credential and a serverless function rather than a rewrite.

That is what a build log is for. The interesting part of a migration is not the final commit; it is the sequence of things you believed on Tuesday that turned out to be false by Thursday. Three of those, in order of how much they changed:

The dependency you cannot see is the one that kills you. “No backend” was never true. The backend was Moralis', and the coupling was invisible precisely because it was so convenient. What made this survivable was that the app was coupled to Moralis the shape — fetch balances, list transfers, route a swap — rather than to Moralis the company. Those shapes have other providers behind them. But note where the final bill actually arrived: not in the effort of rewriting the hooks, which was the cost everyone budgets for, but in six critical advisories riding into the production bundle on a transitive dependency of a vendor that had already stopped existing. The lesson is not “self-host everything,” which no side project can afford. It is to know which shape you are renting, so you can price the replacement before you need it.

Sequence by dependency, not by category. The plan ordered the work by reads then writes, and gated all of it on a key. The real split ran along “does this need an indexer,” which cut across reads and writes both and left two thirds of the work doable with no credentials at all — the difference between blocked for weeks and 19 files down to 3. Then it happened a second time, on an axis the plan did not have at all. The last three files were scheduled by feature order; they were actually finished by what was in the production bundle. Twice in one migration, the useful question turned out to be a different question from the one the plan was sorted by.

Silent failure is the expensive kind. A guard clause returning null, a string comparison against the wrong case, a wei converter applied to an already-decimal number, an explorer lookup handed a decimal id where it wanted hex, three RPC endpoints that were correct when they were written down and have rotted since. None of these throw. Every one renders a page that looks fine, and not one is caught by a lint rule, a unit test or a green build. The only defence found here is unglamorous: call the thing and look at what comes back.

Which is why the swap panel now says it is off, why DataNotice distinguishes “no key configured” from “this chain is not covered,” why the events card admits it has no history, why the price column renders empty rather than plausible, and why vite-plugin-node-polyfills is still installed with a comment explaining what would have to be checked to remove it. A codebase that spent a month being taken apart by its own quiet failures should be the last one to add more of them.
