Engineering for Zero

AWS Free Tier gives you 750 instance-hours and 100 GB of egress a month, and almost no visibility into either. CloudPulse tracks both — built under one hard constraint: it must never cost a single cent to run. That constraint ended up shaping every decision in the stack.

01The Brief: Zero, Enforced

AWS Free Tier has a reporting problem. The allowances are generous — 750 EC2 instance-hours and 100 GB of data transfer out per month — but your consumption of them is effectively invisible until the invoice lands. The Free Tier console is several clicks deep and updates on its own schedule. By the time it tells you anything useful, the billing period is already closed.

CloudPulse puts the two numbers that actually matter for a single-instance footprint, plus live CloudWatch resource metrics, on one page you can leave open in a tab.

But the dashboard is only half the project. The other half is the brief I set myself: the entire system has to run for $0.00/month, indefinitely. Not "cheap." Not "a few dollars." Zero — and enforced by tooling rather than by my own discipline.

That turned out to be the more interesting engineering problem, because a hard cost ceiling propagates into everything. It rules out managed services. It rules out a database. It rules out one of AWS's own APIs. And it converts "don't provision an expensive instance" from a habit you have to maintain into a property the toolchain guarantees.

Here is what that produced.

02One Binary, Three Sources

CloudPulse is a single Go binary. It serves the JSON API and the static frontend from the same process on the same port, with no router, no framework, and no database — 456 lines and six direct dependencies. 

Internet
  │  :80
  ▼
EC2 t3.micro (default VPC, public subnet, IAM instance profile)
  ├── docker: cloudpulse-app  -p 80:8080
  │      ├──→ AWS CloudWatch API  (creds via instance profile)
  │      └──→ api.github.com      (token read from Vault at boot)
  └── docker: vault-server    :8201  (file storage, KV v2)

At boot it initialises three clients in a fixed order, and the ordering is deliberate:

go// main() — the boot sequence is strict and fail-fast
initVault()    // FATAL on failure — no secret store, no application
initAWS()      // returns nil even on failure — deliberate, see below
initGitHub()   // FATAL on failure — token comes from Vault, never the env

http.Handle("/", http.FileServer(http.Dir("./frontend")))
http.HandleFunc("/api/ec2-usage",       ec2UsageHandler)
http.HandleFunc("/api/github-users",    githubUsersHandler)
http.HandleFunc("/api/free-tier-usage", freeTierUsageHandler)

http.ListenAndServe(":" + PORT)

Two things in that sequence are worth pulling out.

Vault comes first, and its failure is fatal. There is no fallback to an environment variable and no degraded mode that quietly skips the GitHub panel. If the secret store is unreachable, the correct behaviour is to refuse to start — a service that boots without its secrets is a service that will surprise you later.

initAWS is the single exception, and it returns nil even when it fails. That isn't an oversight; it's the line that makes local development possible. Its job is to resolve the instance's own ID from the EC2 metadata service at 169.254.169.254 — an address that only exists on EC2. Off-instance, that call should fail. So it fails, logs, falls back to an EC2_INSTANCE_ID_OVERRIDE environment variable, and lets the application boot anyway.

Separating cannot start from starts degraded is a small distinction that pays for itself the first time you try to run the thing on a laptop.

03The Decisions the Budget Made

Every architectural choice below traces back to the same constraint. None of them are defaults:

DecisionRationale
No database, no persistent state A database means RDS, which is not free indefinitely, or self-managed storage on the instance, which is operational overhead for no benefit. Every page load is a live passthrough query. Statelessness fell out of the budget, and it happens to be the right design anyway.
No router, no framework Raw net/http keeps the binary small and the dependency surface auditable — six direct dependencies, all of which I can name and justify. Less to patch, less to audit, and a container that starts fast on a t3.micro.
One binary serving API and frontend No CDN, no second origin, no CORS configuration between them, no separate build pipeline for the UI. The frontend is HTML, CSS and vanilla JS with no build step at all — it ships as files the Go FileServer hands out.
CloudWatch metrics, never the Cost Explorer API Cost Explorer returns real billing data and charges $0.01 per call. On a project whose premise is $0/month, that single line item would have broken the brief. Covered in full in the next section.
Secrets from Vault at runtime AWS Secrets Manager is a per-secret monthly charge. A self-hosted Vault container on the same instance costs nothing and demonstrates the full secret lifecycle rather than an API call.
Terraform validation blocks on cost-bearing variables The instance type accepts t2.micro or t3.micro and nothing else; the EBS volume accepts 8–30 GB. An out-of-budget configuration cannot be planned, let alone applied.

04Cost-Driven API Design

AWS will happily tell you exactly what you have consumed. The Cost Explorer API returns real billing data broken down by service, and it is the correct source of truth for a question like "how much of my free tier is left?"

It also costs $0.01 per request.

On a dashboard, that is a metered subscription to the answer. One page load every ten minutes is roughly $4.30/month — not much money, and also infinitely more than zero. The brief said zero.

So the free-tier panel derives its numbers from CloudWatch instead, which is free at basic-monitoring resolution: elapsed time in the current billing month for the hours figure, and a daily-period sum of NetworkOut subtracted from the 100 GB allowance for egress.

And then — this is the part that matters more than the arithmetic — the panel says exactly what it is.

What the free-tier panel measures, and what it doesn't
  • Hours are elapsed time in the billing month, which assumes one instance running continuously. It is an upper bound on consumption, not a measurement of runtime.
  • Egress is summed for this instance, while the real allowance is account-wide across all services.
  • The 750 and 100 caps apply to legacy Free Tier accounts; AWS moved new accounts to a credits-based plan in July 2025.

That is a deliberate trade: exact numbers that cost money, versus free numbers that are directionally right and clearly labelled. For an early-warning signal — which is all this panel is meant to be — the free version does the job. What it must never do is masquerade as an invoice, so both the API documentation and the UI say so plainly.

"Being explicit about the error bars on a derived metric is worth more than the metric."

The same principle shows up one level further down. When CloudWatch returns no datapoints for a metric — which happens routinely; memory requires the CloudWatch Agent to be installed — the API returns the string "N/A" in a numeric field rather than 0: 

json{
  "InstanceID": "i-0xxxxxxxxxxxxxxxx",
  "cpu":        1.234,
  "memUsed":    "N/A",        // no CloudWatch Agent — absence, not zero
  "netIn":      152340,
  "netOut":     98120
}

It is an unusual shape for a JSON API and it is the right one here. A zero is a measurement. "N/A" is the absence of one, and the frontend checks for that sentinel explicitly before it will parse anything as a number. A dashboard that silently renders missing data as zero is worse than useless — it is confidently wrong, on the one panel you built specifically so you would not have to think about the problem.

05Secrets at Runtime, Not Build Time

The GitHub token never appears in an environment variable, a build argument, a config file, or the container image. It is fetched at boot from HashiCorp Vault, from a KV v2 mount, using a policy-scoped token.

That is a deliberately production-shaped choice on a portfolio-sized project, and the value was in having to learn the whole lifecycle rather than the demo:

01
Dev mode vs. production mode
vault server -dev auto-unseals and keeps everything in memory — fine locally, useless deployed. The deployed instance runs file storage, which means operator init, storing the unseal keys somewhere safe, and unsealing deliberately after every restart. Learning why that difference exists is most of the point.
02
KV v2, not KV v1
Versioned secrets live at kv/data/<path> rather than kv/<path>. The API path and the CLI path differ, which produces a confusing 404 the first time and never again.
03
A policy-scoped token, never root
The application authenticates with a token carrying a cloudpulse-app policy that grants read on exactly one path. The blast radius of that credential is one secret — which is the entire reason to run a secret store rather than a config file.
04
AWS credentials never touch Vault at all
They resolve through the SDK's default credential chain — an IAM instance profile in deployment, ~/.aws locally. There is no static AWS key anywhere in the application, the image, or the pipeline. The right way to hold an AWS credential is to not hold one.

The remaining weak link is the Vault token itself, which reaches the container as an environment variable — which means the deployment still has one long-lived credential in it. The production answer is Vault's AWS auth method: the application authenticates using its own IAM instance profile and receives a short-lived token in return, removing static credentials from the deployment entirely. That is the next iteration, and the one I find most interesting.

06Infrastructure That Refuses to Cost Money

Everything is Terraform: security group, IAM role, policy, instance profile, and the instance itself. The default VPC, its subnets, and the Amazon Linux AMI are read as data sources rather than created, because there is no reason to manage what you can look up.

The part I would point at first, though, is eight lines in variables.tf:

hclvariable "ec2_instance_type" {
  type    = string
  default = "t3.micro"

  validation {
    condition     = contains(["t2.micro", "t3.micro"], var.ec2_instance_type)
    error_message = "Instance type must be free-tier eligible."
  }
}

That is the difference between a rule and a guardrail. A comment saying use a free-tier instance type is advice, and advice is only as good as your attention at the moment you ignore it. A validation block means terraform plan will not produce a plan containing a t3.large — not during a hurried change, not at 2am, not ever. The EBS volume carries the same guard: 8–30 GB, or the plan fails.

"A dashboard tells you what already happened. A validation block decides what is allowed to happen. Only one of those works while you're asleep."

Cost control usually gets built as monitoring — budgets, alerts, dashboards — all of which fire after the money is spent. Pushing the constraint down into the provisioning layer means the expensive mistake never gets made in the first place. Those eight lines are the reason the $0.00 at the top of this page is a fact rather than an intention.

07Shipping It

The image is a multi-stage Docker build. The first stage compiles on golang:1.25-alpine; the final stage is Alpine plus one statically-linked, symbol-stripped binary and the frontend directory: 

dockerfile# build stage — produce a static binary with no debug symbols
RUN CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
    go build -ldflags="-s -w" -o /cloudpulse .

# runtime stage — Alpine, one binary, the static frontend
FROM alpine:latest
WORKDIR /app
COPY --from=builder /cloudpulse /cloudpulse
COPY frontend ./frontend
CMD ["/cloudpulse"]

One detail that matters and is easy to get wrong: the build context is the repository root, not backend/, because the image needs frontend/ as well as the Go source. Building from inside backend/ fails, and the error is not especially forthcoming about why. 

Push to main
  │
  ▼
GitHub Actions
  ├── checkout, setup-go 1.25, module cache keyed on go.sum
  ├── verification build
  ├── buildx → push Docker Hub (GHA layer cache, mode=max)
  └── SSH to EC2 → pull → replace container → prune

All ten credentials the pipeline needs live in GitHub Secrets; none are in the repository. A small piece of trivia that costs an afternoon if you don't know it: GitHub reserves the GITHUB_ prefix for secret names, so the repository owner and name are passed as GIT_OWNER and GIT_REPO even though the application reads them as GITHUB_OWNER and GITHUB_REPO.

08Designing for the Failure Cases

Most of the genuinely interesting work in a service that depends on three external APIs is deciding what happens when they don't answer. These were the cases I designed for explicitly:

  • Independent per-card failure. The frontend issues three parallel fetches with independent error handling. A CloudWatch problem degrades one card to Error while the other two render normally. One dead dependency should never blank a page.
  • A 2-second timeout on the metadata call. 169.254.169.254 is a link-local address; off AWS, connecting to it doesn't fail fast, it hangs until TCP gives up — which on some stacks is around two minutes. An explicit deadline turns a mystery into an instant, logged fallback.
  • Missing datapoints render as "N/A", never 0. Absence and zero are different facts and the API refuses to conflate them.
  • Nil-safe projection of GitHub responses. Every field on the client library's user struct is a pointer. A small safeDeref helper means an unexpected nil becomes an empty string rather than a panic in a handler.
  • Explicit validation of Vault paths. The mount/path split is checked before use, so a typo produces a clear error instead of an opaque API failure at boot.
  • No auto-refresh, deliberately. The refresh interval is switched off. Each page load fans out to three upstream APIs, and a polling dashboard left open in a tab is a quiet way to burn through API quota. Refreshing is a page reload — honest about what it costs.

The operational lesson worth passing on

Vault in file-storage mode seals itself on every restart — dev mode auto-unseals, production mode does not, and that is by design. It means an instance reboot leaves the application unable to boot until someone unseals the vault. Knowing that before it happens at an inconvenient moment is the difference between a five-minute fix and an hour of confusion, and it is the strongest argument for moving to IAM-based authentication.

09The Next Iteration

What exists today is a complete delivery chain on a zero-dollar budget: code, container, infrastructure as code, pipeline, runtime secrets, and enforced cost limits. What I would build next is about hardening and operability.

  • NextVault AWS auth method. Replace the static token with IAM-based authentication and short-lived credentials, removing the last long-lived secret from the deployment. The highest-value change available.
  • HardeningExplicit server timeouts. ReadTimeout, WriteTimeout and IdleTimeout on a configured &http.Server{} rather than a bare ListenAndServe — five lines that close a real slow-request exposure on a public port.
  • OpsA /healthz endpoint. A prerequisite for a load balancer, a container health check, or any meaningful probe.
  • OpsAn Elastic IP. Free while attached to a running instance, and it ends the class of breakage where a stop/start changes the address out from under every config that references it.
  • PlatformECS Fargate and ECR. Rolling deploys with automatic rollback, and no SSH key in CI at all. Needs the health endpoint first.
  • PlatformRemote Terraform state. S3 with DynamoDB locking, versioned and encrypted, so the project stops being single-operator.
  • QualityTests. The three clients are package-level globals; extracting an interface per client makes the handlers straightforward to exercise with httptest and gate in CI.
  • SecurityA narrower IAM policy. The current policy grants more actions than the code calls, and the code only ever reads. Trimming it to the two CloudWatch read actions makes the least-privilege claim an earned one.

Why the Constraint Was the Point

The dashboard was the excuse. The constraint was the actual project.

A $0.00/month ceiling sounds like a limitation, and for the first day it is. After that it becomes a design tool. It eliminates entire categories of solution before you can waste a weekend on them. It forces you to justify every dependency out loud. And it pushes you toward the boring, durable choices — one binary, no state, free metrics, secrets fetched rather than baked in, and limits enforced in the provisioning layer instead of alerted on after the fact.

The result is small enough to hold in your head and complete enough to have every link in the chain present and working. That combination is rarer than it should be, and it is the thing I would want someone to take away from the repository.
